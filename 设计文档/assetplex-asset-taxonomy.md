# AssetPlex 资产分类法（Asset Taxonomy）

> 版本: 1.0 | 日期: 2026-08-15 | 状态: 已定稿
>
> 本文档定义 AssetPlex 产品的资产边界、分类标准和扩展路线。是产品的战略级文档，所有功能设计和技术实现都应以此为准。

---

## 一、设计目标

AssetPlex 的核心价值是**让用户掌控自己的AI资产，换工具不丢东西**。

要达成这个目标，必须回答两个问题：
1. **AI工具有哪些核心资产？** — 决定 AssetPlex 管理什么
2. **这些资产在切换工具时的迁移成本有多高？** — 决定 AssetPlex 优先管理什么

本文档回答第一个问题，并用"迁移成本"作为分类标准。

---

## 二、分类标准：按迁移成本分级

我们用"**切换工具时丢失这个资产的痛感**"作为分类标准，因为：

- 用户关心的不是"工具里有什么文件"，而是"我换工具时哪些东西能跟着走"
- 越痛的资产，越值得 AssetPlex 管理
- 不可迁移的资产，强行管理反而增加复杂度

按这个标准，资产分为 4 个梯队：

| 梯队 | 迁移成本 | 痛感 | 管理策略 |
|------|---------|------|---------|
| 🎯 第一梯队 | 低（语义级迁移即可） | 高（不带走就用不了工具） | ✅ 必须管理 |
| ⚠️ 第二梯队 | 中（需要格式转换） | 中高（丢了要重写工作流） | 🟡 建议管理 |
| 🔴 第三梯队 | 高（格式碎片化） | 极高（丢了多年积累的知识） | 🔴 强烈建议管理 |
| ⚫ 第四梯队 | 不可迁移 | 低（重新配置即可） | ❌ 不管理 |

## 三、资产分类总表

### 🎯 第一梯队：核心可迁移资产（当前已管理）

切换工具时必须带走，否则"换工具=从零开始"。

| 资产类别 | Code | 说明 | 跨工具兼容性 | 当前状态 |
|---------|------|------|-------------|---------|
| **身份** | `identity` | AI 角色认知、人设、行为准则 | ⭐⭐⭐⭐ 高（语义级迁移） | ✅ 已管理 |
| **技能** | `skill` | 领域知识、代码风格、专业能力描述 | ⭐⭐⭐⭐⭐ 极高（Markdown 通用） | ✅ 已管理 |
| **规则** | `rule` | 编码规范、安全约束、输出要求 | ⭐⭐⭐⭐⭐ 极高（规则可转译） | ✅ 已管理 |
| **MCP服务器** | `mcp` | 外部工具集成（数据库、API、文件系统） | ⭐⭐⭐⭐ 高（MCP 是标准协议） | ✅ 已管理 |

> 注：`agent`（只读盘点）与 `memory`（完整写管理，add-memory-category）已作为一等类别接入资产中心，
> 所以声明源合计 7 条而非 4 条；类别清单以 `src/core/asset-categories.ts` 为唯一真相。

### 🧭 元资产：裁决准则（criterion，跨梯队）

不是喂给工具的业务资产，而是「管理其他资产的依据」：存在 Hub 的 `criteria/<slug>.md`，
带 frontmatter（name/description/priority/enabled/appliesTo/source），按优先级组装进大模型 prompt。

| 资产类别 | Code | 说明 | 消费场景 | 当前状态 |
|---------|------|------|---------|---------|
| **裁决准则** | `criterion` | 业内最佳实践条目（Token 效率、规则单主题等） | 冲突仲裁（已上线）；资产诊断（已上线）；市场策展（规划中） | ✅ 已管理（准则页 CRUD + 内置准则包 7 条） |

设计约束：准则本身也是文件资产，CRUD 全走通用 /api/files 通道，不另建写库通道；
仲裁/诊断均为 advisory-only（只给建议），落盘永远由用户确认触发。

### ⚠️ 第二梯队：扩展资产（部分管理，待补全）

切换工具后恢复原工作流的关键，丢失后要重新构建。

| 资产类别 | Code | 说明 | 跨工具兼容性 | 当前状态 |
|---------|------|------|-------------|---------|
| **斜杠命令** | `command` | 自定义命令（如 `/generate-test`、`/commit`） | ⭐⭐⭐⭐ 高（本质是"提示词+参数"） | ❌ 不做（单工具专属，D3 拍板）：仅 Claude Code 有等价机制，已从扫描器移除 `commands/`，资产中心任何位置不出现该类别 |
| **子代理** | `agent` | 子代理配置（专门处理某类任务的子 AI） | ⭐⭐⭐ 中（模型选择可能不同） | 🟢 只读盘点已覆盖多工具（TRAE 内置 persona / 用户自建、Claude、Codex、CodeBuddy expert、插件 agent），暂未纳入保险箱写管理 |
| **提示词模板** | `prompt` | 复杂提示词模板库（重复使用的） | ⭐⭐⭐⭐ 高（文本即可） | 🔴 未管理 |
| **智能体定义** | `agent-config` | 完整智能体定义（模型/温度/工具集） | ⭐⭐ 低（工具专属字段多） | 🔴 未管理 |

### 🔴 第三梯队：隐性资产（未管理，强烈建议补全）

用户花最多时间积累，但最容易丢的资产。

| 资产类别 | Code | 说明 | 跨工具兼容性 | 当前状态 |
|---------|------|------|-------------|---------|
| **长期记忆** | `memory` | 用户偏好、项目决策、踩过的坑 | ⭐⭐⭐⭐ 高（文本即可） | ✅ 已管理（add-memory-category）：Hub `memory/` 为一等类别（order 55），历史 `preferences/` 只读并入并标「旧目录」，可查看/新建/编辑/同步/体检；TRAE `memory/*.md` 已归位 |
| **知识库** | `knowledge` | 项目知识库、文档索引、RAG 数据 | ⭐⭐ 低（格式差异大） | 🔴 未管理 |
| **项目上下文** | `project-context` | 项目级规则、技术栈约束 | ⭐⭐⭐⭐ 高（文本即可） | 🟡 已有「项目」只读视图（TRAE 项目清单 + AI 工具标记 + 项目内规则/技能/文档统计 + git 状态 + 快捷打开），项目级资产本身尚未入库管理 |
| **工作流** | `workflow` | 自定义工作流（多步骤AI任务） | ⭐⭐ 低（概念模型差异大） | 🔴 未管理 |

### ⚫ 第四梯队：工具专有资产（不管理）

无法跨工具迁移，强行管理反而增加复杂度。

| 资产 | 为什么不管理 |
|------|-------------|
| UI 偏好（主题、布局、字体） | 工具专属，不构成"能力" |
| 快捷键绑定 | 工具专属键位映射 |
| 账号/认证（OAuth Token、API Key） | 隐私数据且会过期 |
| 本地缓存（模型缓存、向量索引） | 重新生成即可 |
| 会话窗口状态（当前打开的标签页） | 瞬时状态，非资产 |

## 五、扩展路线图

### Phase A：核心4类（当前已完成）

管理：`identity`、`skill`、`rule`、`mcp`

**目标**: 解决"换工具能不能继续干活"的问题。

**状态**: ✅ 已实现，正在做 UI 重构（v2 设计方案）

**技能出处轴（provenance）五值**：每个已入库技能带一个出处标记，用于资产视图筛选与「来自」徽章。五值闭集，前端导航/后端类型/筛选均按动态扩展、不写死个数：

| 值 | 界面词 | 含义 |
|----|--------|------|
| `self` | 自建 | 用户自己创建/项目工作区内技能（含 vault 内无前缀来源） |
| `marketplace` | 市场 | 从工具市场导入 |
| `plugin` | 插件 | 随插件安装带入 |
| `builtin` | 内置 | 工具/环境自带（资产侧 vs 环境侧归位：builtin 属环境侧，不入资产侧出处序） |
| `github` | GitHub 源 | 从公开 GitHub 仓库经「技能发现」锁 commit 后确认入库（vault source 串 `github:{repo}@{sha}:{skillPath}`），本版新增 |

> 前向兼容：旧版 AssetPlex 遇 `github:` 前缀条目会由 `deriveProvenance` 回落为 `self`（无迁移）。同名冲突本版仅「跳过/覆盖（覆盖前备份）」，「AI 整合新旧两版」为待办不在本版。

### Phase B：扩展3类（UI 重构完成后）

新增：`command`、`agent`、`memory`——**现状：`memory` ✅ 已落地（add-memory-category）、`agent` 🟢 只读盘点已接入、`command` ❌ 不做（D3）**

**目标**: 解决"换工具能不能恢复原工作流"的问题。

**具体改动**:

| 改动点 | 详情 |
|--------|------|
| 类型定义 | `AssetCategory` 已加 `'memory'`（`agent` 走只读盘点；`command` 不加，D3） |
| Adapter | 每个工具补全 scan 范围（WorkBuddy/CodeBuddy/TRAE 已接 memory 映射；Claude 的 `commands/` 规则已移除） |
| Scanner | 扫 `memory/`（含兼容目录 `preferences/`）与 `agents/`；**不扫** `commands/` |
| 前端 | 资产库左侧导航支持动态类别，不是写死 4 个（已实现：清单唯一声明源在后端，侧栏/快照/筛选自动跟随） |
| 数据迁移 | 无需迁移旧数据（向后兼容；`preferences/` 只读并入不搬家） |

**新增资产类别详细定义**:

#### `command`（斜杠命令）——❌ 不做（D3 拍板）
- **不做的理由**: 只有 Claude Code 有等价机制，其他工具无对应概念，强行入库只会得到一套"只能给一个工具用"的类别；它更接近单工具的高频操作入口，不是跨工具可迁移的能力资产
- **现状口径**: 扫描器已移除 `commands/` 规则；资产中心侧栏/快照/筛选/收藏向导/切换页均不出现「命令」；Hub 里已有的 `commands/` 历史文件仍在磁盘，只是不再作为资产呈现
- **原设想**（存档）: 用户自定义的高频操作，如 `/generate-test`、`/commit`；Markdown 格式，含命令名、参数定义、提示词模板

#### `agent`（子代理配置）
- **是什么**: 专门处理某类任务的子 AI 配置（如"代码审查专家"）
- **格式**: Markdown 文件 + 可选 JSON 配置
- **扫描位置**:
  - Claude Code: `~/.claude/agents/*.md`（已扫）
  - Codex: `~/.codex/config.toml` 中的 agents 字段（未扫）
  - TRAE: 暂无对应概念
- **跨工具兼容性**: 中（模型选择/工具集可能不同，但角色定义可迁移）

#### `memory`（长期记忆）——✅ 已管理（add-memory-category）
- **是什么**: 用户偏好、项目决策、踩过的坑
- **格式**: Markdown 文件
- **Hub 位置**: `memory/`（新建只写这里）；历史 `preferences/` 作为兼容目录只读并入，卡片标「旧目录」，不自动搬家（D2）
- **扫描/分发位置**:
  - TRAE: `~/.trae-cn/memory/*.md`（`user_profile.md` 仍归身份）
  - WorkBuddy / CodeBuddy: `~/.workbuddy/memory/`（已接入映射）
  - Claude Code: `~/.claude/memory/*.md`（未扫，待后续变更）
- **能力口径**: 查看/筛选/搜索、新建与编辑、同步（仅支持的工具，不支持则显示原因并禁用）、资产医生体检（正文 8000 字符阈值）
- **跨工具兼容性**: 高（纯文本）

### Phase C：隐性资产（远期）

新增：`knowledge`、`project-context`、`workflow`

**目标**: 解决"换工具能不能带走多年积累的隐性知识"的问题。

**难点**:
- `knowledge` 各工具格式差异大（Qoder 用 `.qoder/knowledge/`，其他工具可能用向量库）
- `project-context` 需要引入"项目"概念，AssetPlex 需要从"工具级管理"扩展到"项目级管理"
- `workflow` 概念模型差异大，需要抽象出统一的工作流模型

**建议**: 等 Phase A、B 跑通后再启动，且需要单独的 spec 来定义"项目"这个新概念。

## 五之二、管家层：资产治理（add-asset-governance）

分类法回答「管什么」，管家层回答「管得好不好」。它不属于任何资产梯队，而是跨梯队的**治理能力**，只读聚合、按需写库：

| 能力 | 定位 | 写库边界 |
|---|---|---|
| 健康分（四维：完整性/规范性/分发/唯一性） | 让「家底好不好」可度量、可下钻 | 只读，缓存本地 |
| 一键整改 | 机械项批量修复、语义项给草案 | 逐项确认后写，写前备份，可撤销 |
| 重复治理 | 完全/近重复分组 → 合并草案 → 归档式执行 | 只归档不删除，灰区必须人工勾选，可还原 |
| 主动性建议 | 首页最多 3 条可执行 + 1 条信息项 | 零写库、零模型调用 |
| MCP 第二入口 | 让 Agent 宿主在会话内读写同一份 Hub | 两段式（propose→commit），TTL 10 分钟，默认不分发 |

治理能力的共同红线：
- **建议与执行分离**：所有模型输出、扫描结论都只是建议，落盘/分发必须用户显式触发。
- **可逆**：写前备份、归档不删除、批次记录可撤销。
- **不打扰**：无问题不硬凑建议；灰区不自动执行；跨类别永不合并。

## 六、设计原则

基于本分类法，AssetPlex 在设计时应遵循以下原则：

### 1. 资产类别可扩展
- 前端导航、后端类型、数据库 schema 都不能写死 4 个类别
- 新增类别应该是"加配置"而不是"改代码"

### 2. 工具能力差异要尊重
- 不是所有工具都有所有资产类别（如 Qoder 没有用户级 identity）
- UI 上要显示"该工具支持哪些类别"，而不是强行让所有工具对齐

### 3. 资产类别的优先级
- 第一梯队是 P0，必须有
- 第二梯队是 P1，UI 重构后立即补
- 第三梯队是 P2，远期规划
- 第四梯队永远不做

### 4. 跨工具兼容性是核心指标
- 资产管理不仅是"存进来"，还要"分发出去"
- 分发时如果目标工具不支持某类资产，要明确告知用户
- 例如：把 Claude Code 的 `commands/` 同步到 TRAE 时，TRAE 不支持斜杠命令，应该提示用户

## 八、界面词汇表（spec refactor-design-system terminology）

界面文案一词一义，全站统一。后端字段值、文件名、配置键不动，仅约束**用户可见文案**。

### 核心词

| 术语 | 含义 | 出现位置 |
|------|------|----------|
| **我的库** | 已入库（收藏）到 Hub 的资产集合，即库内资产 | 库状态分段控件、工具来源徽章（hub→我的库）、收藏入口「收藏到我的库」 |
