# asset-pipeline.spec.md：单资产流水线（诊断 → 治理 → 分发）

> capability: 资产详情工作台、布局分级、诊断摘要与成本可见、上下文保持、就地修复与复检、分发衔接、降级、隐私
> 变更: refactor-asset-pipeline | 决策依据: proposal.md D1-D8
> 适用面：资产库内走详情面板的类别（rule / identity / memory 及后续同类）；技能与智能体专属视图不在本规格内
> 口径对齐：诊断与证据以 `add-diagnosis-rules/specs/diagnosis-rules.spec.md` 为准；
> 修复与分发的信任红线以 `add-asset-doctor/specs/fix-and-distribute.spec.md` 为准；导航以 `refactor-home-action-panel/specs/navigation.spec.md` 为准

## 定义

- **资产详情工作台**：资产库右侧/全屏的详情面板。本规格要求它同时承载"看内容、看体检、改问题、送出去"四件事。
- **单资产流水线**：诊断 → 治理（修复）→ 复检 → 分发，四步都在资产详情内完成，不切换到全局治理页。
- **诊断摘要**：对某个资产"上一次成功诊断"的结论摘要——结论（健康 / 需关注 / 有风险）、问题数与其中高严重度数、可修复数、诊断时间、是否仅机械结论。
- **三要素**：资产正文、适用准则集、模型名。任一变化，上一次诊断的语义结论即视为失效。
- **有效（摘要）**：三要素与上次诊断时完全一致，此时再发起诊断不会调用模型。
- **过期（摘要）**：三要素至少一项已变，上次结论仍可展示但必须标注"上次结果"并说明变化原因。
- **从未诊断**：该资产在本机没有任何成功诊断记录。
- **就地**：结果不通过跳转页面呈现；不离开详情即可看到下一步动作与结果。
- **本批修复**：一次确认所应用的一组修复（可能包含多条问题）。本批可整体撤销。
- **复检**：修复写库成功后自动对新正文重新发起的一次诊断。
- **分发**：把资产正文写入已安装且支持该类别的工具目录（不含任何网络上传）。

## ADDED Requirements

### Requirement 1：版面按「空 / 单 / 多」分级，单资产不再要求二次点击

**用户可见行为**：一个资产的时候别摆一张孤零零的卡；没有资产的时候别摆空网格；多资产才需要网格。

#### Scenario 1.1 空类别只有一个出口

- **Given** 某类别下没有任何资产
- **When** 用户进入该类别
- **Then** 内容区展示居中的空态：说明"我的库里还没有〈类别名〉"+ 一句为什么值得收藏
- **And** 只提供一个主操作（从已安装工具收藏该类资产）
- **And** 不展示筛选栏、分页、详情占位或空白网格

#### Scenario 1.2 单资产类别进入即展开

- **Given** 身份类别下只有 1 个资产
- **When** 用户点击侧栏该类别
- **Then** 该资产的详情直接展开，正文可见，无需再点击卡片
- **And** 列表区仍保留该资产的一张卡并呈选中态，卡片不拉伸成整行
- **And** 宽屏下呈现"窄列表 + 详情"双栏，详情占据主要可读宽度

#### Scenario 1.3 用户关闭后本次停留不重开

- **Given** 单资产类别的详情已自动展开
- **When** 用户按 Esc 或点击关闭
- **Then** 详情收起，列表回到常规态，该唯一卡片上出现明确的"展开详情"入口
- **And** 用户在该类别内后续操作（搜索、切换筛选、再点别的卡片）不会自动重新展开该资产

#### Scenario 1.4 多资产保持网格，详情不挤没列表

- **Given** 某类别下有 12 个资产
- **When** 用户进入该类别并点击其中一项
- **Then** 列表以自适应网格呈现（窄屏单列、宽屏多列），被点资产高亮
- **And** 详情展开后列表仍保留可用宽度（不至于被压到看不见或每行只剩图标）
- **And** 详情展开/收起不导致列表整体重新排序或滚动跳变

#### Scenario 1.5 切换类别清理上一条上下文

- **Given** 用户正在查看规则类别下某个资产的详情
- **When** 用户切到记忆类别
- **Then** 上一个资产的详情关闭，不残留其正文或诊断结果
- **And** 搜索词与筛选回到该类别的初始状态，列表回到顶部
- **And** 若记忆类别只有 1 个资产，按 Scenario 1.2 自动展开它

### Requirement 2：详情首屏就能回答「上次结果如何、这次要不要花钱」

**用户可见行为**：不点按钮也知道上次体检结论与有效期；点之前就知道会不会调用模型。

#### Scenario 2.1 打开详情即有摘要

- **Given** 某资产上次诊断过（结论"需关注"，4 个问题，其中 1 个高严重度，2 个可修复）
- **When** 用户打开该资产详情
- **Then** 首屏显示摘要：结论徽标、问题总数与高严重度数、可修复数、上次诊断时间
- **And** 摘要与正文同屏可见，不需要先点"资产医生"

#### Scenario 2.2 结果有效时明说「不会调用模型」

- **Given** 摘要判定为有效（三要素均未变）
- **When** 用户查看摘要
- **Then** 摘要标注"结果有效（内容、准则、模型均未变）"
- **And** 主按钮为"重新诊断"，旁注"命中缓存，不会调用模型"
- **When** 用户点击"重新诊断"
- **Then** 结果就地刷新并再次标注"未调用模型"，不出现"调用 N 次"的提示

#### Scenario 2.3 结果过期时说清哪一项变了

- **Given** 用户刚编辑过该资产正文（或刚改过适用准则、刚更换模型）
- **When** 用户回到详情查看摘要
- **Then** 摘要标注"上次结果，已过期"并列出变化项（正文已变更 / 准则集已更新 / 模型已更换）
- **And** 主按钮为"重新诊断"，旁注"本次将调用 1 次模型"
- **And** 过期结论仍带"上次结果"前缀，不被误读为当前结论

#### Scenario 2.4 未配置 AI 时不把「没评估」说成健康

- **Given** 用户未配置 AI 端点
- **When** 用户查看摘要
- **Then** 摘要显示机械 / 静态规则结论，并标注"语义质量未评估"
- **And** 主按钮文案为"运行检查（不调用模型）"，不出现任何调用次数提示
- **And** 提供配置 AI 的入口（到达可填写端点与密钥的位置）

#### Scenario 2.5 诊断进行中与完成

- **Given** 用户点击"重新诊断"
- **When** 诊断进行中
- **Then** 按钮进入加载态并禁用重复点击，详情不关闭、不滚动跳走
- **When** 诊断完成
- **Then** 摘要与问题列表就地替换为新结果，摘要中的时间同步更新
- **And** 页面不因结果刷新而丢失当前滚动位置

#### Scenario 2.6 所有会花钱的动作都提前报数

- **Given** 详情内存在可能触发模型的入口（重新诊断、生成修复草案、修复后自动复检）
- **When** 用户即将触发其中任一动作
- **Then** 触发点附近可见"将调用 1 次模型"或"命中缓存，不消耗调用"
- **And** 不存在"点了才知道要花钱"的入口

#### Scenario 2.7 编辑保存后立即标为过期

- **Given** 用户在详情内编辑并保存了该资产正文
- **When** 保存完成回到查看态
- **Then** 摘要立即变为"上次结果，已过期（正文已变更）"
- **And** 不自动发起诊断（不隐式花钱）

### Requirement 3：诊断与修复全程留在资产详情，且可回到来源

**用户可见行为**：点一次医生不会把你踢到治理大页面；从别处进来能直接看到这个资产，返回能回去。

#### Scenario 3.1 诊断不离开详情

- **Given** 用户在资产详情内
- **When** 用户执行诊断、生成草案、应用修复、复检、分发
- **Then** 每一步的进行状态与结果都出现在当前详情内
- **And** 不发生整页跳转到全局治理页，也不打开与当前资产无关的页面

#### Scenario 3.2 从治理页直达单资产

- **Given** 用户在全局治理页展开了某个资产的问题报告
- **When** 用户点击"在资产库中打开"
- **Then** 进入该资产所属类别，并直接打开该资产详情，诊断摘要可见
- **And** 地址栏可反映出"这是哪一个资产"（可复制、可分享给同一台机器的另一个窗口）

#### Scenario 3.3 从首页待办直达单资产

- **Given** 首页待办中有可修复问题，标注"去资产库修改"
- **When** 用户点击该入口
- **Then** 进入该资产详情（而不是只到类别列表），摘要显示上次结论
- **And** 该链接指向的资产在库内不存在时，落到类别列表并提示"该资产可能已被移动或删除"

#### Scenario 3.4 返回回到来源页面

- **Given** 用户从治理页或首页进入资产详情
- **When** 用户点击返回（浏览器后退或详情内的返回）
- **Then** 回到来源页面，来源页面的筛选、展开与滚动位置不丢失
- **And** 不出现"返回后又被弹回详情"的循环

#### Scenario 3.5 直接输入单资产地址

- **Given** 用户拿到形如 `<类别地址>?asset=<库内相对路径>` 的地址
- **When** 在地址栏直接打开
- **Then** 页面加载后直接展示该资产详情与摘要
- **And** 关闭详情后地址回到该类别列表（不新增多余的历史记录）

#### Scenario 3.6 地址里的资产不存在

- **Given** 地址中的资产路径在库内不存在或已越界
- **When** 页面加载
- **Then** 展示类别列表并提示"资产不存在或已被移动"，不白屏、不报错堆栈
- **And** 不因该地址向诊断服务发起请求

#### Scenario 3.7 用户主动去全局治理再回来

- **Given** 用户在资产详情内点击"查看全局治理"
- **When** 从全局治理页返回
- **Then** 回到原资产详情，摘要与已展开的问题状态保留
- **And** 全局治理页仍是独立页面，不被详情替代

### Requirement 4：问题就地展开、就地修复、修复后自动复检

**用户可见行为**：每条问题能看到依据与原文证据；改完立刻知道还有没有毛病；一次撤销能回退这一批。

#### Scenario 4.1 问题行展开证据与建议

- **Given** 报告含一条"description 过泛"的问题
- **When** 用户展开该问题
- **Then** 分区展示：规则编号与规则名、严重度、置信度、来源（机械检查 / 静态规则 / AI 判断）、证据（库内相对路径 + 行号 + 原文片段）、建议改法
- **And** 证据片段与建议文案分区呈现，不混成一段文字
- **And** 证据中的路径为库内相对路径，不暴露本机绝对路径

#### Scenario 4.2 证据不足不下结论、不给修复

- **Given** 某条问题被标记为"证据不足，无法确定"
- **When** 用户展开它
- **Then** 明确显示"证据不足，无法确定"，视觉上弱于有证据的结论
- **And** 不提供"应用修复"，不把它算作可修复问题数

#### Scenario 4.3 由问题生成草案（库内零变化）

- **Given** 报告中有 3 条可修复问题
- **When** 用户勾选其中 2 条并点击"生成修复草案"
- **Then** 展示可编辑草案全文与逐条修复说明（对应哪条建议改在哪）
- **And** 明确提示"此阶段库内暂无变化"
- **And** 草案生成失败时就地显示原因与"返回重选"，详情不关闭

#### Scenario 4.4 一屏确认，且提前披露复检成本

- **Given** 草案已就绪（可能被用户编辑过）
- **When** 用户点击"应用"进入确认
- **Then** 同一屏内可见：当前库内版本对照、最终草案、同步目标工具清单、旧版将进备份区的说明
- **And** 明确提示"保存后将自动复检（本次将调用 1 次模型）"
- **And** 身份类资产额外红字警示：改写会影响所有工具中的人格设定

#### Scenario 4.5 写库后自动复检

- **Given** 用户确认应用修复
- **When** 写库成功
- **Then** 自动发起一次复检，复检过程可见（"复检中"），期间不关闭详情
- **When** 复检完成
- **Then** 报告就地替换，并给出一句对比结论（如"已修复 2 项，剩余 1 项"）
- **And** 复检失败时，保留"已写入资产库"的事实，单独提示复检失败原因与"重试复检"

#### Scenario 4.6 本批撤销

- **Given** 一次修复成功写库
- **When** 用户查看结果区
- **Then** 提供"撤销本次修复"，说明将把库内恢复为修复前的版本
- **When** 用户确认撤销
- **Then** 库内恢复旧版，结果区标注"已撤销"
- **And** 摘要立即变为"结果已过期（已撤销）"，**不自动**发起复检、不产生新的模型调用
- **And** 已分发到工具的内容若需回退，按工具逐项提供回滚入口

#### Scenario 4.7 写库失败与部分成功

- **Given** 用户确认应用，但写库失败或部分工具分发失败
- **When** 结果返回
- **Then** 就地如实展示：写库是否成功、每个工具的结果与失败原因
- **And** 写库失败时草案与勾选项保留，可直接返回确认屏重试
- **And** 不出现"看起来全部成功"的汇总

#### Scenario 4.8 不可修复项只有建议

- **Given** 报告中某条问题为纯建议项
- **When** 用户查看该问题
- **Then** 标注"需人工判断"，不提供勾选与草案入口
- **And** 仍可查看其证据与建议

### Requirement 5：复检通过后就地出现分发入口，结果就地可见

**用户可见行为**：改好了就在原地送出去；哪个工具成功、哪个失败、能不能重试，一眼看清。

#### Scenario 5.1 复检通过 → 主入口出现

- **Given** 复检完成，未发现高 / 中严重度问题（或仅剩低严重度与建议项）
- **When** 复检结果呈现
- **Then** 详情内出现主按钮"分发到工具"
- **And** 用户在详情内点击即可打开工具清单，不需要回到列表卡片或跳到同步页

#### Scenario 5.2 复检未通过不藏风险

- **Given** 复检仍有高或中严重度问题
- **When** 用户查看结果
- **Then** 主分发按钮不出现，提示"还有 N 个问题未处理"
- **And** 仍提供一个次要入口"仍要分发"，并注明当前风险
- **And** 不因用户选择分发而隐藏"仍有问题"的事实

#### Scenario 5.3 工具清单说清能不能同步

- **Given** 用户打开分发入口
- **When** 工具清单加载
- **Then** 每个工具显示：显示名、安装状态、该资产类别的支持情况、当前同步状态
- **And** 未安装或类别不支持的工具不可选，并给出原因（例如"此工具不支持该类别"）
- **And** 默认勾选已安装、支持类别且已启用的工具

#### Scenario 5.4 就地展示逐工具结果

- **Given** 用户对 3 个工具执行分发
- **When** 执行完成
- **Then** 结果就地列出：已写入并校验 / 已跳过 / 失败（附原因）
- **And** 提供"回滚本次分发"的可用性说明（有成功写入项时可用）

#### Scenario 5.5 失败项单独重试

- **Given** 3 个工具中 1 个失败
- **When** 用户点击"重试失败项"
- **Then** 只对失败的那个工具重新执行，成功项不重复写入
- **And** 重试结果就地更新该行状态

#### Scenario 5.6 同步状态回到真值

- **Given** 分发完成后用户关闭详情查看列表
- **When** 资产卡渲染
- **Then** 卡上的同步徽标反映真实结果（与分发索引一致），不沿用分发前的旧状态
- **And** 不出现"提示成功但列表仍显示未同步"的自相矛盾

#### Scenario 5.7 确认屏已勾选分发时不重复询问

- **Given** 用户在修复确认屏勾选了目标工具
- **When** 应用完成
- **Then** 直接展示逐工具分发结果，不再二次弹窗要求确认分发

### Requirement 6：降级与空态说清原因，不伪装成功

**用户可见行为**：没 Key、没缓存、诊断挂了、工具不支持，都要一句话说清"现在能做什么"。

#### Scenario 6.1 没有 AI 也能改格式类问题

- **Given** 用户未配置 AI 端点
- **When** 用户打开详情
- **Then** 摘要显示机械 / 静态结论并标注"语义未评估"
- **And** 若存在可机械判定的可修复问题，仍可走修复流；否则明确"当前只能做确定性检查"

#### Scenario 6.2 从未诊断

- **Given** 该资产没有任何诊断记录
- **When** 用户打开详情
- **Then** 摘要显示"尚未诊断"，不显示任何结论徽标
- **And** 主按钮为"开始诊断"，并提示"本次将调用 1 次模型"（已配置 AI 时）

#### Scenario 6.3 诊断失败

- **Given** 诊断请求失败（网络错误 / 模型输出非法 / 资产文件读取失败）
- **When** 失败返回
- **Then** 就地显示失败原因，并提供"重试"
- **And** 若存在上一次成功结果，继续展示并明确标注"上次结果"
- **And** 资产正文与分发状态零变化

#### Scenario 6.4 分发不可用

- **Given** 没有任何已安装且支持该类别的工具，或所有工具都未启用
- **When** 用户查看分发入口
- **Then** 按钮禁用并说明具体原因（无已安装工具 / 类别不支持 / 均未启用）
- **And** 提供"去连接工具"入口
- **And** 不展示空白的工具清单，也不假装分发成功

#### Scenario 6.5 非库内条目

- **Given** 该条目是环境条目或路径无法解析到库内
- **When** 用户打开详情
- **Then** 不显示诊断与分发入口，显示"该条目不在库内，无法诊断与分发"
- **And** 正文仍可查看

#### Scenario 6.6 资产文件已消失

- **Given** 用户打开详情后，文件在磁盘上被移动或删除
- **When** 用户发起诊断或分发
- **Then** 提示"文件已不存在，可能已被移动或删除"，并提供刷新列表
- **And** 不把它显示为"健康"或"无问题"

#### Scenario 6.7 摘要读取失败不拖垮详情

- **Given** 摘要读取失败（本机记录损坏或接口异常）
- **When** 详情渲染
- **Then** 正文与其它功能正常可用，摘要区显示"最近诊断信息暂不可用"
- **And** 不阻塞页面加载、不显示伪造的结论或时间

### Requirement 7：宽窄屏布局与键盘主链路

**用户可见行为**：手机宽度也能一条路走完；只动键盘也能诊断、修复、分发。

#### Scenario 7.1 宽屏双栏

- **Given** 视口宽度 ≥1280px
- **When** 详情打开
- **Then** 列表与详情并排常驻，详情宽度稳定在可读区间
- **And** 详情内正文、摘要、问题区域各自可独立滚动，互不挤压消失

#### Scenario 7.2 中屏折中

- **Given** 视口宽度 1024–1279px
- **When** 详情打开
- **Then** 列表与详情仍并排，但问题证据默认折叠、分发结果默认折叠为摘要行
- **And** 用户可逐项展开，不需要横向滚动

#### Scenario 7.3 窄屏覆盖

- **Given** 视口宽度 <1024px
- **When** 用户打开详情
- **Then** 详情全屏显示，提供返回入口，关闭后回到列表原位置
- **And** 诊断、修复、分发的主操作在到达对应区域后可直接触达，不因长度被挤到不可见处

#### Scenario 7.4 键盘可完成主链路

- **Given** 用户全程只使用键盘
- **When** 依次执行：聚焦资产卡 → 打开详情 → 发起诊断 → 展开问题 → 生成草案 → 确认应用 → 分发
- **Then** 每一步都可用 Tab / Shift+Tab 到达，用 Enter 或 Space 触发
- **And** 确认类操作不得仅靠鼠标可点，也不得被自动聚焦的正文区吞掉

#### Scenario 7.5 焦点不丢、结果可播报

- **Given** 用户用键盘触发了诊断或修复
- **When** 操作完成、界面局部更新
- **Then** 焦点保持在触发元素上，不被重置到页面顶部
- **And** 结果区以礼貌播报方式告知结论变化（如"诊断完成：4 个问题"）
- **When** 用户按 Esc 关闭详情
- **Then** 焦点回到打开详情的资产卡

#### Scenario 7.6 语义与颜色无关

- **Given** 屏幕阅读器用户浏览详情
- **When** 焦点进入摘要、问题列表、修复结果、分发结果
- **Then** 每个区域有可读名称（如"体检报告""修复流""分发结果"）
- **And** 结论与严重度不只用颜色表达，文字与徽标同时可读

### Requirement 8：隐私边界不扩大，文案与实际一致

**用户可见行为**：本地能做的绝不上网；用 AI 也只去你自己配置的端点；界面说的发送范围和实际一致。

#### Scenario 8.1 未配置 AI 时零网络

- **Given** 用户未配置 AI 端点
- **When** 打开详情、运行检查、修复可机械判定的问题、分发
- **Then** 不发起任何模型请求，全部在本机完成
- **And** 界面不出现"已发送到云端"之类暗示

#### Scenario 8.2 只为用户自配端点

- **Given** 用户配置了自己的 OpenAI 兼容端点
- **When** 发起诊断、生成草案、自动复检
- **Then** 请求只发往该端点，不经过任何产品方中转
- **And** 设置处明确说明"AI 为可选增量，关闭后确定性检查仍完整可用"

#### Scenario 8.3 文案不得比实际更窄

- **Given** 诊断实际发送了资产正文（或只发送了命中片段，取决于当前发送面）
- **When** 界面展示隐私说明
- **Then** 说明文字与实际发送范围一致，不宣称"只发片段"而实际发全文
- **And** 本变更不得扩大发送范围（不新增字段、不新增第三方、不新增额外资产）

#### Scenario 8.4 分发完全本地

- **Given** 用户执行分发
- **When** 写入工具目录
- **Then** 全程本地文件操作，不经过任何网络端点
- **And** 分发结果只在本机记录

#### Scenario 8.5 摘要记录只在本机

- **Given** 系统保存了"上次诊断摘要与指纹"
- **When** 任何网络请求发生
- **Then** 该记录不进入请求体，也不上传
- **And** 记录内容不包含资产正文、绝对路径或用户身份信息

## 非功能约束

- **首屏成本**：详情打开只允许一个摘要读取请求；不引入轮询、不因摘要而阻塞正文渲染。
- **零隐式花费**：除用户明确确认的"自动复检"外，任何打开页面、切换类别、查看报告的行为都不得触发模型调用。
- **口径单一**：问题、证据、置信度、忽略的展示必须与全局治理页同源同义，不出现"详情说 4 条、治理说 6 条"。
- **文件规模**：新增/改动的组件遵守项目 300 行文件上限，超出即拆分。
- **隐私**：本规格、契约与任务清单中的示例一律使用中性名（`demo-identity`、`example-rule`、`testuser`），不得出现真实资产名、真实目录或绝对路径。
