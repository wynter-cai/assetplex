# fix-and-distribute.spec.md：一键修复与分发（写链路）

> capability: 改写草案、应用确认（diff + 分发勾选）、写库备份、swap 分发复用与回滚
> 变更: add-asset-doctor | 决策依据: proposal.md D2/D4；信任红线同仲裁（模型永不自主落盘）

## 定义

- **改写草案**：针对报告中 `fixable=true` 的问题，模型基于资产原文生成的修订版本（可整体采纳、可逐段编辑）
- **应用修复**：用户显式确认后 ①旧版入备份区 ②草案写入资产本体（走各类别既有写库路径）③可选分发
- **分发**：对已安装该资产的每个目标工具，走既有 swap 单资产预览-备份-执行-验证链路；医生不自建第二条通道

## Scenario 1：从报告生成改写草案

- **Given** 诊断报告含至少一条 fixable 问题
- **When** 用户点「生成修复草案」（可选中只修复部分问题）
- **Then** 展示草案全文（可编辑文本域）+ 逐问题"修复说明"（对应哪条建议改在哪）；此阶段库内资产零变化

## Scenario 2：应用确认一屏化（proposal D4）

- **Given** 草案已就绪（可能被用户编辑过）
- **When** 点「应用并分发」
- **Then** 确认对话框同屏展示：①修改前后 diff ②分发目标工具清单（默认全部已安装该资产的工具，可逐个取消，也可全部取消只改库）③旧版将存入备份区的说明；一次确认后依次执行

## Scenario 3：写库带备份可回滚

- **Given** 用户确认应用
- **When** 写库执行
- **Then** 旧版本先进备份区再覆盖（复用 swap 备份语义与保留策略）；报告面板出现「撤销本次修复」入口，点击后库内恢复旧版（分发侧回滚走 swap 回滚，见 Scenario 5）

## Scenario 4：分发逐工具结果如实报告

- **Given** 确认时勾选了分发，目标为 3 个已安装工具
- **When** 分发执行
- **Then** 逐工具显示结果（已写入并校验 / 跳过 / 失败+原因）；某工具失败不影响其他工具；全部完成后资产卡的"已分发工具"状态刷新为真实结果

## Scenario 5：分发失败与回滚入口

- **Given** 分发到某工具时目标路径存在冲突或写入失败
- **When** 执行中止该项
- **Then** 该项走 swap 既有冲突确认语义（不静默覆盖）；已成功的工具项提供整体「回滚本次分发」（swap rollback 恢复备份）；库内本体不受分发失败影响（写库在分发前已完成且独立）

## Scenario 6：只改库不分发

- **Given** 用户在确认框取消了全部工具勾选
- **When** 应用
- **Then** 仅写库+备份，任何工具目录零变化；下次正常同步/切换时新版随大流分发（不隐式承诺分发）

## Scenario 7：草案只对本次已见内容负责

- **Given** 资产超长（超出诊断时进 prompt 的截断上限），草案基于截断内容生成
- **When** 用户查看草案
- **Then** 明确警示"内容超出审视范围，草案仅覆盖前段，应用前请人工确认未审部分"；超长资产默认禁用「生成草案」（保留诊断与建议），避免破坏未审内容

## Scenario 8：批量修复谨慎化（不提供）

- **Given** 批量体检后多条资产带 fixable 问题
- **When** 用户浏览报告清单
- **Then** 不提供"全部一键修复"——批量只到诊断为止，修复/分发逐条走 Scenario 2 确认（写链路有意保持单点审批，防止一次误点污染多个资产与工具）

## Scenario 9：隐私边界

- **Given** 草案生成请求发出
- **When** 传输
- **Then** 与诊断同一边界：资产原文 + 适用准则 + 修复指令发往用户自配端点；分发执行完全本地，不经任何网络端点
