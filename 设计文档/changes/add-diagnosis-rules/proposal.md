# proposal: add-diagnosis-rules（规则优先、AI 增量的资产深度诊断）

> 级别：S（新增规则引擎模块 + 证据模型 + 治理中心口径变更）
> 状态：待维护者审核
> 输入：`设计文档/research/research-ai-deep-diagnosis-2026-11-14.md`（怎么诊断）、
> `research-ai-asset-authoring-2026-11-14.md` 及三份分册（诊断什么算好）
> 依赖：add-asset-doctor（诊断/草案/apply/备份/分发）、add-asset-governance（健康分/建议/去重）、
> add-llm-conflict-arbitration（准则资产 / LlmClient / AI 配置）

---

## 为什么做（背景）

1. **现有体检是「准则驱动的自由发挥」**：`doctor.ts` 把资产全文与准则丢给模型，输出 `criterion/finding/suggestion` 三段文字。结论没有稳定编号、没有原文定位，用户无法复核，也无法回归——同一份资产换一次模型就可能换一套说法。
2. **调研结论明确：业内没有成熟的「纯 LLM 体检」**。可规模化的形态都是「确定性规则先筛 → LLM 只做解释、影响与改法」，且证据链（文件 + 行/片段 + 触发规则）是可信任度的地基。LLM 在「是否符合自然语言规格」上系统性高估缺陷，让它多解释反而更不准。
3. **诊断标准已经完备**：P1-5 三份分册给出了七类资产共 75 条可落地检查项（人设 12 / 规则 12 / 技能 15 / MCP 10 / 命令 8 / 子代理 9 / 记忆 9）。去重归并后落成 71 条规则（63 条类别专属 + 8 条跨资产通用），缺的不是知识，而是把知识变成 **ruleId + 判定信号 + 建议 + 来源** 的稳定规则集。
4. **治理中心已经在等这份规则**：`assetplex-home-and-governance-proposal.md` §5.3 明确「每条检查项都必须带 ruleId + 判定信号 + 建议 + 来源，同一份规则同时驱动诊断与资产编写指南，避免两套口径」。现在 `governance-health.ts` 的规范性维度只有 4 条机械项，撑不起「按资产类型做细」。

## 目标

| # | 目标 | 用户可见结果 |
|---|------|--------------|
| G1 | **每条结论可回溯到一条规则** | 问题卡显示「规则编号 + 规则名 + 来源依据」，可点开看这条规则为什么存在 |
| G2 | **机器判零模型调用** | 未配置模型时，格式、长度、引用、密钥、冲突信号等静态规则完整可用 |
| G3 | **AI 只做语义增量且必须带证据** | AI 项标「AI 判断」，附文件 + 行 + 原文片段；证据不足显示「无法确定」，不给结论、不计分 |
| G4 | **误报可控** | 默认只展示高置信项；支持忽略，忽略后同一内容不再提示；忽略条数在报告中如实披露 |
| G5 | **诊断与编写指南同源** | 治理中心分类页、资产详情、编写指南读到的是同一份规则集，口径永不漂移 |
| G6 | **结果可回归** | 报告携带规则集版本；固定标注集跑基线，规则或提示词变更后差异可比较 |

## 范围

### 做

- 规则注册表：`diagnosis-rules.yaml`（本变更产出，71 条，覆盖七类资产 + 8 条跨资产通用规则）
- 静态规则执行：判定信号 → 命中 → 生成带证据的 finding，零模型调用
- AI 增量执行：只对静态命中项与候选规则做语义判断，输出必须从候选 ruleId 中选且带证据
- 证据模型：`evidence[]`（库内相对路径 + 行号 + ≤200 字片段）、`confidence`、`insufficientEvidence`
- 误报控制：高置信默认视图、忽略清单（本地、按内容哈希失效）、向导 Top 3
- 规则集版本与回归：`rulesVersion` 入报告，标注集 + 回归脚本
- 七类资产的分类视图数据口径（治理中心 tab 用）

### 不做

- ❌ 不做「纯 LLM 体检」或让 AI 直接产出健康分（分数只由规则计算，AI 不参与打分）
- ❌ 不做云端口碑/众包规则、不做规则市场
- ❌ 不做代码级数据流分析（资产是提示词/配置，不是可执行代码）
- ❌ 不做「AI 自动改资产」链路扩展——修复仍走既有 `doctor-fix` 草案 → 用户确认 → 备份 → 应用
- ❌ 不在本变更内做 MCP 工具描述的运行时监控（只做静态扫描；运行时归后续变更）
- ❌ 不引入新的 LLM 供应商/网关（复用用户自配的 OpenAI 兼容端点）
- ❌ 不做规则可视化编辑器（一期规则集随产品版本内置）

| 现有能力（文件/契约） | 处置 | 说明 |
|---|---|---|

| `doctor-mechanical.ts` 的 `mechanical:description-empty` | **复用** | 并入 `SK-03` / `CMD-02` 的判定信号，不再单独记一条 |

| `doctor.ts` 的 LLM 语义诊断（自由 `issues[]`） | **扩展 + 部分冲突** | 保留调用链与缓存，但输出改为「候选 ruleId 闭集 + 证据」；自由文本 `finding` 仅作展示，不再是无编号结论。旧 `criterion` 字段保留兼容 |

| `doctor-fix.ts` / `doctor-apply.ts` / `doctor-backup.ts` / 分发 | **复用** | 不改写链路；仅新增约束：无证据或无 ruleId 的 finding 不可 `fixable` |
| `doctor` 批量体检 / estimate 预算护栏 | **复用** | 静态规则不消耗调用，估算数只统计 AI 增量项 |
| `criteria.ts` 准则资产 | **复用（限权）** | 准则只作为「团队偏好」叠加到建议文案与 LLM 提示，**不得新增 ruleId**，否则又变两套口径 |
| `governance-health.ts` 规范性维度 | **扩展** | 由「机械项 + 语义项」改为「按规则聚合的 findings」，按严重度与置信度加权；评分构成可解释 |
| `governance-health.ts` 唯一性维度 + `duplicates.ts` | **复用（并规避双扣）** | `DUP-01` 不参与规范性计分，重复只由唯一性维度扣一次 |
| `governance-health.ts` 四维权重与降级 | **复用** | 未配置模型时语义规则标「未评估」，不按 0 分计 |
| `governance-suggestions.ts` | **复用 + 扩展** | 新增一条「高置信规则命中」建议来源，仍遵守最多 3 条可执行 |
| `governance.ts` `/issues` 下钻 | **扩展** | 返回项补 `ruleId`、`evidence`、`confidence`，前端可直达原文行 |
| 用户自配端点 / `LlmClient` 隐私边界 | **复用** | 仍只发往用户自配端点；新增「只发证据片段与元数据」的发送层约束 |
| 忽略清单（忽略后不再提示） | **新增** | 本地文件存储，按 `ruleId + 路径 + 内容哈希` 失效；不上传 |
| 标注集与回归脚本 | **新增** | 固定样本 + 指标对比，不阻断 CI，只报差异 |
| 规则注册表与 `/rules` 只读接口 | **新增** | 供治理中心分类页与编写指南共用 |
| 资产编写指南（按类型一页） | **新增** | 与规则同源，避免「文档一套、诊断一套」 |

- 复用：7 项
- 扩展：7 项
- 新增：4 项（忽略清单、标注集与回归、规则注册表接口、编写指南页数据）
- 冲突：1 项（`shouting-rules`，待裁决）

## 关键决策

- **D1 规则是唯一裁判**：所有 finding 必须绑定 `ruleId`。AI 只能对已有规则做「是否成立 + 影响 + 改法」的增量判断，不能凭空造规则。
- **D2 静态优先**：71 条中 45 条可纯静态判定，26 条需要语义判断。静态规则永不因未配置模型而缺席。
- **D3 证据优先于结论**：证据不足时输出 `insufficientEvidence=true`，文案固定为「证据不足，无法确定」；不计分、不可修复、不进入建议。
- **D4 通用规则去重**：跨资产共性（密钥、注入、断链、时效、空洞表述、冲突、载体、重复）收敛为 8 条通用规则，用 `appliesTo` 表达适用范围；在任一类别 tab 下展示，但全库统计只计一次。
- **D5 严重度沿用三级**：`high / medium / low` 与现有 `DiagnosisSeverity` 对齐，调研的 P0/P1/P2 一一映射，避免既有评分与前端徽章二次改造。
- **D6 规则集随版本内置**：规则由产品随版本发布，用户不可逐条编辑（可关闭整体 AI 增量、可忽略单条命中）。规则集是产品承诺，不是用户配置。
- **D7 忽略不等于修好**：忽略只影响展示与计分，报告必须显示「已忽略 N 条」并提供恢复入口，杜绝「沉默健康」。
- **D8 口径单一**：同一份 `diagnosis-rules.yaml` 同时驱动诊断、治理分类页、编写指南。任何新检查项必须先加规则，再谈展示。

## 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 静态规则误报（阈值类） | 用户不信诊断 | 阈值取官方硬线；提示类规则默认 low 且折叠；报告披露规则依据 |
| LLM 过度判错 | 虚假结论 | 闭集约束 + 证据校验 + 默认只展示高置信 + 证据不足不下结论 |
| 规则膨胀导致维护成本 | 规则腐烂 | 每条规则带来源；标注集回归；规则只增删不静默改语义 |
| 与准则资产形成两套口径 | 用户困惑 | 准则限权为偏好层，不得新增 ruleId |
| 与重复治理双扣分 | 分数失真 | `DUP-01` 不参与规范性维度，重复只在唯一性扣一次 |
| 隐私外泄 | 事故级 | 默认本地；只发证据片段；BYOK；忽略清单与反馈不上传 |
| 示例数据照搬本机 | 事故级 | 所有夹具用中性名（`demo-skill`、`testuser`、`example-rule`） |

## 回滚

按任务分阶段提交：①规则注册表与静态执行器（只读）②证据模型与路由兼容 ③AI 增量 ④忽略清单 ⑤治理口径切换 ⑥回归与指南。任一阶段回退后，医生旧链路（`issues[]`）仍可用；③回退后自动回到「机械项 + 自由语义」的旧行为，数据零损坏。

## 开放问题（待维护者确认，附推荐）

1. **`mechanical:shouting-rules` 无调研依据** → 推荐**从新规则集移除**（D8 要求每条规则有来源；无来源规则不进闭集。旧 doctor 链路可保留该机械项不动，不纳入新规则集与治理计分）。
2. **是否引入第四级 `critical`** → 推荐**不引入**，保持 `high/medium/low` 三级；密钥/注入/投毒用 `high` + 专属标记展示，避免动既有评分权重、徽章与排序。
3. **是否允许用户关闭单条规则** → 推荐**不允许**；规则集是产品承诺（D6），关闭单条会破坏口径单一与回归基线。用户有 finding 级「忽略」即可满足降噪诉求，且忽略条数如实披露（D7）。

> 已确认：治理中心的「应用修复」一期允许直接改文件，但必须先备份、支持单条与批次撤销（维护者 2026-11-15 拍板）。本变更的修复链路仍复用既有 `doctor-fix` 草案 → 用户确认 → 备份 → 应用，不新增自动改文件能力。
