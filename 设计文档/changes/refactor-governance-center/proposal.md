> 级别：S（页面重定位 + 新聚合接口 + 批量编排 + 规则/忽略管理入口）
> 状态：待维护者审核（spec / tasks 通过后才写代码）
> 来源：维护者 2026-11-15 拍板（待办池 B22）；同时收口 B17（规则按需加载 / 用户自定义）与 B18（裁决准则迁移）
> 前置：`add-asset-governance`（四维健康分 / 一键整改 / 重复项）、
> `add-diagnosis-rules`（71 条规则 / 证据 / 忽略，T4–T5 尚未实施）、

> `refactor-skill-catalog`（技能模块内分类与批量，已写 spec 未实施）

## 为什么做

维护者已拍板的四条结论（2026-11-15）：

1. 定位 = **全局体检报告 + 跨类别批量 + 规则/忽略管理**；
2. 命名 = **质量中心**，原 `/governance` 替换式重定向；
3. 批量分工：质量中心做**跨类别**批量，各资产模块只保留**模块内**分类与批量；
4. 单资产修复全部沉到资产详情，质量中心不重复，只给「在资产库中打开」深链；裁决准则并入。

现状四个硬缺口（读码结论）：

| 事实 | 位置 | 对本变更的含义 |
|---|---|---|
| `/governance` 是只读临时容器，页头写着「治理中心建设中」 | `web/src/pages/Governance.tsx` | 入口已占位，等待被替换 |
| 该页点击问题行会**就地展开 `DiagnosisPanel`**，一次点击即触发一次诊断 | `web/src/components/governance/DimensionIssues.tsx` | 与「单资产修复归详情」直接冲突；且丢失上下文、成本不可预期 |
| 批量能力两处并存：技能页「全部体检」+ 治理页「一键整改」，前者只诊断、后者只修复，口径与上限各说各话 | `web/src/components/doctor/SkillsCheckupSection.tsx`、`src/server/routes/remediation.ts` | 用户不知道该去哪；skill 页 spec 已声明跨类别批量归质量中心 |
| 71 条规则、忽略清单、按资产类型按需加载都只有引擎与契约，没有用户入口 | `src/core/diagnosis-*.ts`、`add-diagnosis-rules` T4–T5 待排 | 规则是产品承诺，却看不见、管不了 |

一句话：把「治理」从一堆入口收成一个**质量中心**，它只回答「整体怎么样、先改哪一类」；「这一个怎么改好」回资产详情。

## Goal

打开质量中心，用户可以在同一页内完成：

> 看到全库体检结论（四维分数 + 可解释构成）→ 看到问题按类型聚类的排序（哪一类最值得先修）→ 选类别或选问题类型发起跨类别批量诊断（发起前知道缓存命中与需调用）→ 对可修复项生成影响清单、一次确认批量修复、整批可撤销 → 管理内置/自定义规则与忽略清单 → 进入裁决准则。

验收标准：

1. **命名与入口收口**：侧栏与页面只出现「质量中心」；旧 `/governance` 地址替换式重定向，不留第二套入口。
2. **先看整体再动手**：问题按类型聚类可读，能回答「9/18 是技能缺 description」，排序规则可解释。
3. **成本先算后跑**：任何批量发起前都有预估（缓存命中 vs 需调用）；成本未知时按钮不可用。
4. **批量可回退**：修复有影响清单、二次确认、备份与整批撤销；诊断只读不动内容。
5. **单条不重复**：质量中心任何问题行都没有「应用修复」，只有深链；单条修复只在资产详情。
6. **口径单一**：待处理数与首页状态条、侧栏徽标同源；规则集与资产详情、编写指南同源。

## 三层分工（拍板结论，必须写进实现）

| 层 | 回答的问题 | 只做什么 | 明确不做 |
|---|---|---|---|
| **首页** | 今天该干什么 | 异常驱动的 ≤3 条待办 + 四个状态数字 + 最近变化 | 不做全量问题清单、不做批量、不做规则管理 |
| **资产详情** | 这一个怎么改好 | 诊断 → 修复 → 复检 → 分发（单资产闭环） | 不做跨资产对比与聚类、不做批量 |
| **质量中心** | 整体怎么样、先改哪一类 | 四维体检报告、问题聚类与排序、跨类别批量诊断/修复、规则与忽略管理、裁决准则入口、重复项 | 不做单条修复、不内嵌单资产体检面板、不就地编辑资产 |

边界落地方式：

- 质量中心的每条问题/聚类只渲染**深链**（`/vault/<类别>?asset=<库内相对路径>`），点击进入资产详情继续处理；
- 资产详情保留「查看质量中心」入口，但只用于跳回全局视角，不把质量问题搬进详情；
- 同一能力只允许一处有写操作：单条修复只在详情；跨类别批量只在质量中心；模块内（技能）批量只在技能页。

## Scope

### 做

1. **命名与路由**（R1）：页面与导航改名「质量中心」；主路径 `/quality`；旧 `/governance`、`/governance/*` 替换式重定向；首页、窄屏摘要、页面标题同步。
2. **全局体检报告**（R2）：复用四维健康分；新增按问题类型（ruleId / 规则标题）的跨资产聚类、影响面 × 修复成本排序、诚实空态与未评估披露。
3. **跨类别批量诊断**（R3）：按类别多选 + 按问题类型多选；发起前预估（缓存命中 / 需调用 / 不可诊断 / 语义跳过）；可并发执行、结果两层聚合、失败项可单独重试。
4. **跨类别批量修复**（R4）：影响清单 → 二次确认 → 复用既有整改引擎（草案 → 备份 → 写库 → 可选分发）→ 汇总 → 整批撤销。
5. **规则与忽略管理**（R5）：内置规则只读浏览、按类别筛选、按需加载披露、用户自定义规则（覆盖 / 追加，坏规则跳过并告警）、忽略清单与恢复、规则集版本提示。
6. **裁决准则迁入**（R6）：`/quality/criteria` 承接现有 `CriteriaView`；资产库不再列出该类别；`/vault/criteria` 替换式重定向；后端 criteria API 与数据目录不动。
7. **与单资产详情边界收口**（R7）：移除质量中心内嵌体检面板，改为深链；补「同一能力唯一归属」约束。
8. **降级与空态**（R8）：无 LLM Key / 规则校验失败 / 批量超限 / 部分失败 / 数据缺失 / 重复提交，全部明说原因。

### 不做

- ❌ **不做单条修复、不内嵌单资产体检面板**：这是 `refactor-asset-pipeline` 的职责，质量中心只给深链。
- ❌ **不新造批量修复引擎**：计划 / 执行 / 撤销全部复用 `/api/governance/remediation/*`，本变更只扩展「按规则过滤」与「影响清单字段」。
- ❌ **不做技能模块内的分类与批量**：技能页的看板、按来源/用途分组、诊断选中 / 分发选中归 `refactor-skill-catalog`，本变更不碰。
- ❌ **不做自动修复 / 定时体检 / 后台轮询**：任何写库都必须一次显式确认。
- ❌ **不新增诊断规则**：规则集内容归 `add-diagnosis-rules`；本变更只做浏览、按需加载与用户自定义入口。
- ❌ **不删除重复项页**：重复项仍是质量中心组的子项，页面与接口不动。
- ❌ **不改健康分权重与算法**：四维权重（30/30/25/15）与不适用重归一化沿用既有 spec。
- ❌ **不改分发与备份通道**：批量修复的 `distribute` 仍走既有 apply 分发与 swap 回滚入口。
- ❌ **不做移动端专属重排、命令面板、趋势报表**。

## 关键决策

- **D1 一个任务一个入口**：跨资产总览与批量只在质量中心；单资产闭环只在详情；模块内批量只在模块页。三处不互相复制按钮。
- **D2 聚类键优先规则编号**：聚类优先按 `ruleId` 合并（同一规则在多资产上的命中算一类）；规则编号缺失时（`add-diagnosis-rules` T5 未落地）退化为「规则标题归一化」，并在界面标注「按标题聚合」，不假装是规则编号。
- **D3 排序可解释、可复算**：先按**影响面分**（受影响资产数 × 严重度权重 high 3 / medium 2 / low 1）降序；同分按**预计调用次数**升序；仍相同则按类别声明顺序。全静态类永远排在同影响面的语义类之前。界面提供「为什么这个排序」说明。
- **D4 成本未知不得发起**：预估接口失败、缺字段、超过上限，按钮禁用并给原因；预估必须同时给出「缓存命中」与「需调用」，只有合计不给拆分视为不合格。
- **D5 批量上限沿用既有硬线**：修复单批 20 个资产（`REMEDIATION_BATCH_LIMIT`，服务端硬上限，不允许前端放水）；诊断单次 100 个资产、预计调用 > 50 次二次确认、单次硬上限 200 次。超出提示分批，不静默截断。
- **D6 病态数据不伪装**：无 AI 时只跑静态规则并标「语义未评估」；维度数据缺失标「暂不可用」；规则集致命错误直接报错，不展示 0 分或「全部健康」。
- **D7 忽略 ≠ 修好**：忽略只影响展示与计分；报告始终显示「已忽略 N 条」并给恢复入口；忽略随内容哈希失效。
- **D8 命名只改表面**：页面、导航、文案、路由改「质量中心」；后端 API 命名空间仍为 `/api/governance/*`（避免再造一套接口与迁移风险），仅在文档中说明二者对应关系。

## 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 改路由导致收藏/深链失效 | 用户点旧链接 404 | `/governance*`、`/vault/criteria` 全部替换式重定向，逐一写路由用例；重定向表集中一处 |
| 聚类按标题退化导致同类被拆成多条 | 排序失真、用户困惑 | D2：优先 ruleId；退化时界面明确标注「按标题聚合」；规则接口就绪后自动切换，无需改前端 |
| 批量修复误伤 | 多文件同时被改 | 影响清单（含库内路径）+ 二次确认 + 既有备份 + 整批撤销 + 单批 20 上限；默认只改库不分发 |
| 批量诊断烧 token | 用户对成本敏感 | 预估强制拆分缓存命中/需调用；>50 次二次确认；缓存命中项不计费 |
| 质量中心再次膨胀成「什么都做」 | 与详情重复、回归难 | R7 写死「单条修复不在此页」；问题行只在组件层禁止出现修复按钮，并有组件测试守护 |
| 规则/忽略接口未就绪（T4–T5 未落地） | 管理页半残 | 明确降级：显示「规则接口未就绪，暂只读内置规则集版本」，不伪造可编辑能力 |
| 与既有 spec 表述冲突（详情页 Scenario 3.2） | 两处都写「由我负责」 | 本变更以「质量中心只给深链」为准；T9 同步回改对方 Scenario 并跑既有用例 |
| 隐私外泄 | 事故级 | 聚合只输出库内相对路径与中性资产名；夹具一律 `demo-skill` / `example-rule` / `testuser`；提交前跑 `scripts/privacy-check.mjs` |

## 回滚

按 Phase 分 commit：①命名与路由迁移（纯前端）②聚类概览（只读接口）③批量诊断（只读编排）④批量修复（复用写链路 + 过滤扩展）⑤规则与忽略管理 ⑥裁决准则迁移 ⑦边界收口与降级专项。

- 回滚 ⑤：规则管理页隐藏，其余照常；规则引擎不受影响。
- 回滚 ⑥：准则回到资产库类别，`/quality/criteria` 重定向回 `/vault/criteria`。
- 回滚 ④：批量修复入口隐藏，单资产修复与既有 `/remediation/*` 能力完整保留。
- 任一步都不改动诊断引擎、规则集内容、备份格式与分发通道，回滚零数据损坏。

## 待拍板（最多 3 条，附推荐）

1. **质量中心主路径用 `/quality` 还是保持 `/governance`？**
   推荐：`/quality` + `/governance*` 替换式重定向（严格按「原 `/governance` 替换式重定向」的拍板原文）。若维护者希望收藏地址完全不变，只需把路由常量换回 `/governance`，其余 8 个 Requirement 不受影响。
2. **用户自定义规则的落盘位置与写入通道？**
   推荐：`<Hub>/diagnosis-rules/` 目录，内置规则随版本只读；写入复用既有 `/api/files`（与裁决准则新增文件同款通道），保存前调 `POST /api/diagnosis/rules/validate` 校验。不新增 CRUD 路由，避免第二套规则存储。
3. **跨类别批量修复是否需要逐条 diff 预览？**
   推荐：**不需要**。批量只给影响清单（资产、路径、命中规则、预计调用）+ 一次确认 + 备份 + 整批撤销；逐条 diff 只在资产详情（`refactor-asset-pipeline`）提供。若要求批量也逐条预览，单批 20 个资产会产生 20 次模型调用与 20 屏确认，直接违背「成本先算后跑」。
